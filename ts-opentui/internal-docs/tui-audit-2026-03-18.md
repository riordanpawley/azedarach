# TUI Stability Audit (2026-03-18)

## Scope
This audit focuses on `ts-opentui` runtime stability after daemon-first hard-cut changes, with emphasis on:
- startup reliability
- runtime error handling in atom/react integration
- test strategy gaps (unit/integration vs true TUI e2e)

## Executive Summary
1. Your assumption is correct: daemon/backend paths currently have substantially denser test coverage than UI runtime paths.
2. The TUI has no end-to-end test harness today (no `e2e/` suite, no e2e script in `package.json`).
3. Recent startup bugs were not daemon protocol bugs; they were mostly TUI orchestration/cancellation semantics and layer composition regressions.
4. Current UI testing is mostly unit-level formatting/atom tests and does not cover full render/input/session flows.

## Regressions observed in this session
### 1) CLI command no-output / early exit
- Symptom: `az issue list` and `az --version` produced no output in worktree build.
- Root cause: runner-level layer composition (`cliRunner`) created interrupt/requirement mismatch.
- Fix landed: moved provisioning to proper layer boundary; removed problematic global runner provide.

### 2) TUI startup red error spam (`InterruptedException`) + board unavailable
- Symptom: TUI renders but console floods with interrupted-fiber errors and board can degrade to unavailable state.
- Root cause class:
  - expected atom fiber cancellation surfaced as unhandled promise-mode action errors
  - interrupted atom result treated as hard board failure instead of transient loading
- Fix landed:
  - interruption-aware promise guard in app atom actions
  - interruption-aware board render-state mapping

## Coverage Gap Analysis
### A) High-risk runtime paths lacking behavioral e2e coverage
1. Startup/hydration lifecycle (`src/ui/App.tsx`, `src/ui/launch.tsx`)
2. Board data load and refresh transitions (`src/ui/atoms/board.ts`, `src/services/BoardService.ts`)
3. Input-driven flows (keyboard/mouse atoms) under rapid updates/cancellation
4. Overlay orchestration (detail/create/fork/planning/spec/diff interactions)
5. Session monitor startup, reconnect, and waiting-state behavior

### B) Error handling consistency gaps
The UI atom layer has many `Effect.catchAll(Effect.logError)` call-sites. This pattern:
- logs but often masks classification (interrupted vs retryable vs fatal)
- can leave UI in ambiguous state without explicit user-facing fallback semantics

### C) Stub/deferred behavior still present
Examples discovered:
- `src/services/SessionService.ts` has TODO placeholders for lifecycle behavior.
- `src/ui/App.tsx` has TODO markers around disabled functionality.

These are not all active blockers, but they are risk multipliers during refactors because they weaken invariant clarity.

## Current UI tests: what they cover vs miss
### Covered (examples)
- formatting/token/layout helpers
- launch/runtime control helpers
- selected atom behavior (`task`, `pr`, runtime)

### Not covered by true E2E today
- full-screen TUI launch + steady-state board hydration
- keyboard/mouse interaction flows against live daemon
- multi-step user journeys (create task, start session, navigate, overlay open/close, quit)
- failure-injection UX behavior (daemon unavailable, reconnect, cancellation storms)

## Recommended Stabilization Plan
### Phase 1: Observability and deterministic error taxonomy (short)
Acceptance Criteria:
1. No uncaught interrupted-fiber noise in TUI console during normal startup/refresh.
2. Board state transitions use typed/non-fatal classification (interrupted/loading vs fatal/unavailable).
3. Startup failure reason is rendered in a single canonical diagnostic path.

### Phase 2: TUI E2E harness (high priority)
Acceptance Criteria:
1. Add `ts-opentui/e2e` harness capable of launching `bun run bin/az.ts` in PTY.
2. Add golden smoke test: launch -> board ready -> quit cleanly.
3. Add regression tests for:
   - daemon attach success
   - daemon temporarily unavailable then recover
   - interruption storms do not hard-fail board render state

### Phase 3: Critical journey suite
Acceptance Criteria:
1. Keyboard journey: navigate columns/tasks, open/close overlays, quit.
2. Task journey: create/edit/move task via TUI actions with daemon-backed state verification.
3. Session journey: start/pause/resume/stop with read-model confirmation.

### Phase 4: Hardening and debt reduction
Acceptance Criteria:
1. Replace blanket `catchAll(logError)` in critical atoms with typed handlers.
2. Remove or formalize TODO stubs in active runtime paths.
3. Add canary test that fails on reintroduction of runner/layer wiring regressions.

## Proposed Priority Backlog (for issue creation)
1. Build PTY-driven TUI e2e harness and CI command.
2. Add startup smoke e2e (board ready + no interruption spam).
3. Add board-refresh/cancellation e2e regression suite.
4. Refactor atom error handling to explicit interruption/retryable/fatal taxonomy.
5. Remove/replace remaining runtime TODO stubs in session-related services.

## What this means for directing implementation
If your goal is “TUI thin client but production-stable,” the bottleneck is now test architecture, not daemon RPC domain split.
- Daemon/API work made correctness easier to unit/integration test.
- TUI behavior correctness now depends on introducing robust interaction e2e coverage.
